# Field report: driving VoiceOver through this MCP to test another product

Written 2026-09-02 by the agent that used it, immediately after the run. This is
**consumer feedback, not a spec**: what the MCP was asked to do, where it held,
and the six places it sent its user outside the tool to finish the job.

## What the run was

[Acter](https://github.com/marlon-sousa/acter) is an accessibility-first
terminal for screen reader users — Rust and Tauri, Windows first, now growing a
macOS lane. Its process requires that every manual accessibility checklist be
driven against the real window and recorded item by item, and it permits an agent
to check an item it can actually observe through this bridge.

Three checklists were driven here across two days: **M2** (the connect dialog's
Terminal row), **M3** (the macOS menu bar) and **M3.5** (a help topic telling a
VoiceOver user how to configure Quick Nav for a terminal). All of it on **macOS
15.0, VoiceOver, silent capture, the `user` persona**, 2026-09-01 and 09-02.

The run succeeded. It produced five defects in the product under test, corrected a
help topic one commit before it shipped, and closed a roadmap entry that had been
blamed on the product and turned out to be the launch. So nothing below is a
complaint that the tool does not work.

**The contract this is written against** is the one the tool implies: the MCP is
the whole interface to the reader. If a tester needs Apple's plists, VoiceOver
Utility's resource bundles, or this repository's own Swift sources to finish a
run, the MCP has failed, whatever the run produced. Over two days that tester did
all three.

## 1. The handshake changes a blind user's reader settings and does not put them back

`connect_reader` points VoiceOver at the capture voice before it answers, which
the guidance says plainly. On 2026-09-01 at 19:12 the handshake then **failed** at
`captureProof` — "the reader would not take 'describe item in voiceover cursor'
... VoiceOver's scripting object model is not answering" — and the capture voice
was **left selected**. A voice that renders nothing, still selected, on the
machine of the person who depends on it.

No MCP call reports what setup changed, and none puts it back. Recovery meant
reading this repository:
`bridges/voiceover/Sources/VoiceOverBridgeDomain/Controllers/ReaderEdgeSetup.swift`,
then `VoiceOverBridgeAdapters/SpeakSelectionVoiceStore.swift`, to learn that the
selection lives in `~/Library/Preferences/com.apple.SpeakSelection.plist` and must
be export-modify-imported rather than written with `defaults`. The hand edit that
followed destroyed the user's pitch, rate and volume (0.4 / 0.6 / 1.0) and dropped
them from the premium Luciana voice to the compact one. VoiceOver rebuilt the
selection from scratch on its next start and those values are gone.

The misdiagnosis that led there was the tester's own — the mute being chased was
the user's accidental touch gesture. That is exactly the point: **the
misdiagnosis was only possible because nothing in the MCP could say what state the
bridge had left the reader in.**

**Asks.** Make setup transactional: restore the previous voice selection when any
rung of the handshake fails. Expose an inventory of everything setup touches, and
a `restore_reader_settings` call that is safe to run blind. A failed connect must
not be able to cost somebody their voice.

## 2. The recovery text names a recovery that does not work on this machine

Every failure of that kind, and `screenreader://reader-guidance` itself under
"Your session was SET UP before you were handed it", instructs the human to run
`killall VoiceOver && open -a VoiceOver`.

On this Mac `open -a` starts the process and leaves the AppleScript object model
dead: `-1728` to `name of item`, `text under cursor` and `last phrase` alike, so
`captureProof` fails again, forever. What works is the real toggle — **Cmd+F5**,
key code 96 with command down through System Events. Following the bridge's own
advice cost about twenty minutes and an interruption of the blind user at the
machine. First connect attempt 17:01, first working session 19:18.

**Ask.** Either restart the reader the way that works, or print the gesture that
works. The guidance's reason for not restarting somebody's reader unasked is
right; the instruction it gives them instead has to be the one that succeeds.

## 3. There is no way to start the bridge from the MCP

Three sessions across two days opened with

    reader "voiceover": no endpoint answered: local:voiceoverMcpBridge:
    dial unix /Users/marlon/.screenreader-mcp/voiceoverMcpBridge.sock:
    connect: connection refused

resolved each time by leaving the tool, changing directory into this repository
and running `nohup ./.build/debug/BridgeListener`. A tester who has only the MCP —
which is the intended user — is stopped dead there. The message names neither the
binary, nor the repository, nor the command.

**Ask.** Start or adopt the bridge from the server, or make that error name the
exact command that fixes it.

## 4. Nothing in any result says which application you are in

This produced the run's biggest near-miss, and it is the finding worth the most to
you.

Acter was being driven as an **unbundled** debug binary. macOS never makes such a
process the active application — so `go to menu bar` reached **Finder's** menu bar
while Acter held the window and every keystroke. Every value the MCP returned was
consistent with "the application under test has no menus", which was one careless
sentence away from being written into a pull request as a defect in a product that
did not have it. Wrapped in a minimal `.app`, the same build announced its own six
menus immediately.

`get_focus_info` in the same state answered `-25204 cannotComplete — the
application did not answer`, naming no application either. What settled it was
`osascript` and System Events, asking directly which process was frontmost and
enumerating the menu bar by hand: outside the MCP, and outside the `user` persona
the run was supposed to be held in.

**Asks.** Carry the owning application — bundle identifier and name — on every
focus, cursor and menu-bar result. Let a session state the application under test
at `connect_reader` and warn when the reader is somewhere else. One line reading
"menu bar of: Finder" would have saved an hour and prevented a false defect.

The guidance already warns that a wedged application looks like a dead reader, and
that on the maintainer's machine it once was Finder. You know about this failure
mode. Give the tester the field that detects it.

## 5. The reader's configuration surface is out of scope, and that is what shipped wrong text

The guidance covers Quick Nav well **as runtime toggles an agent flips**: the three
command names, that the Left-and-Right chord moves two settings and announces
neither, that the toggles outlive the session. All correct, all useful, and one of
those measurements is dated during this run, so the document is visibly alive.

But the question M3.5 had to answer was not "how do I turn it on". It was **"what
do we tell a blind user to set, and what is that control called on screen"** —
because the shipped deliverable was a help topic that a VoiceOver user would follow
with VoiceOver Utility open in front of them.

The MCP has nothing on that surface. So the tester read
`Commanders-QuickNavTab.loctable` inside `/System/Applications/Utilities/VoiceOver
Utility.app` and wrote the help from Apple's own strings. That file names **four**
controls in a "Quick Nav tab": *Enable arrow-key Quick Nav*, *Enable single-key
Quick Nav*, a *When left and right arrow keys are pressed* choice, and *Always
allow typing in text fields while using single-key Quick Nav*.

Driving the pane with this bridge showed macOS 15 has **two** of them and no such
tab. Quick Nav is a section of the Commanders pane, and it holds the popup **Left
and right arrow keys** — options read out as Toggle both options, Do nothing,
Toggle arrow-key Quick Nav, Toggle single-key Quick Nav, shipping set to toggle
both, which is the entire coupling — and **Always allow typing in text fields**,
ticked by default. There is no *Enable arrow-key Quick Nav* checkbox and no
*Enable single-key Quick Nav* checkbox anywhere on that pane. Help naming them
would have sent a blind user hunting for controls that do not exist.

A string in a resource bundle is not a control on the screen. **This bridge is the
component that knows this reader on this OS release; nobody else is better placed
to say what it exposes.**

**Ask.** A `screenreader://reader-configuration` document: the panes and controls
this reader actually presents, in the reader's own words, stated per OS version
and measured rather than read out of a bundle. A tester should never be reverse
engineering Apple's localisation tables to write a sentence for a blind user.

## 6. Reading state by toggling it mutates the machine, and left an inconclusive result

The guidance is candid that VoiceOver exposes its 45 settings as commands with no
query, that this is the reader's property rather than the bridge's gap, and that
"toggle, and listen to what it says" is the replacement. As an account of
VoiceOver that is fair.

It is still not enough for a test harness, for one reason: **every read is a write
to somebody's computer.** It also cost this run a clean result. The first attempt
at "does `h` type an h in the command line" answered *heading not found*; between
that and the run that passed, both the popup setting and the window focus had
changed, and the run could not separate the two causes. The specification now
records that inconsistency rather than an answer, which is the honest thing to
write and not the thing anyone wanted to measure.

Apple's cooperation is not required to fix it. The bridge already reads
`com.apple.VoiceOver4/default.plist`.

**Ask.** A read-only `get_reader_settings` sourced from the preference file — a
probe that changes nothing, so a measurement can be repeated without moving the
thing being measured.

## 7. Two smaller ones

**Speech comes back in the machine's UI language, with no locale field.**
Everything captured on this machine was Portuguese: "nível de título 2", "botão,
escurecido, este item não está disponível", "incorreta". The checklists it feeds
are English assertions about roles and states, so what ships in a pull request now
rests on the tester's translation of the reader's output. Report the speech locale
at `connect_reader`, and return the language-neutral role and state alongside the
spoken string wherever the bridge already knows them — `get_focus_info` does.

**Facts about the machine were read with `defaults` instead of asked for.**
`com.apple.keyboard.fnState`, to learn whether F1 needed `fn` on this keyboard, and
the configured VoiceOver modifier. Both are properties of the machine the bridge is
already sitting on, and both decide what a keystroke in a checklist means.

## What is genuinely good

Said plainly, because the list above is one-sided by construction:

- **The two-notation `press_gesture` rule** — a command name, or a `kb:` keystroke
  — together with "an unknown command name fails cleanly and changes nothing, so
  guessing is safe" is the best affordance in the tool. It turns the reader's
  vocabulary into something explorable instead of something to be memorised.
- **The persona boundary is right, and the VoiceOver-specific correction to it** —
  that cursor navigation is *inside* the ordinary vocabulary here, unlike on NVDA —
  is precisely the kind of thing only this bridge can tell a tester, and it changed
  how the run was driven.
- **Silent capture works**, and the timestamps are good enough to measure a menu
  opening in 548 ms against a 20-to-68-second figure measured on Windows.
- **The guidance improved between the two days of this run**, citing measurements
  dated during it.

## The pattern

Every complaint above is one thing. **The MCP is excellent at telling a tester how
to press things, and silent about the state of the machine it is pressing them
on** — which application owns the focus, how the reader is configured, and what the
bridge's own setup changed. Close those three and this tester never opens a plist
again.
